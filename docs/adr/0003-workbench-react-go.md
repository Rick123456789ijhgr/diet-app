# 0003. 開發工作台改為 React 前端，經 Go 主伺服器存取，並納入冷啟動上傳工具

- 狀態：提議中
- 日期：2026-10-13
- 決策者：Rick（提議）；待全體組員確認

## 情境

開發工作台原以 Streamlit 實作於 `ai/workbench/`（約 3,800 行），用來以合成影像或開發照片測試模組一的前處理、調整參數、跑 E1 實驗。實際使用後的問題：

- **整頁重跑**：每調一個參數，整支腳本從頭執行，無法只更新結果區；拖動滑桿時反應慢。
- **版面難以控制**：沒有固定左欄、固定高度並各自捲動的雙欄等版面元件，只能以 CSS 覆寫 Streamlit 內部的 `data-testid`，升級後可能失效；字級與間距難以細調，參數與結果無法在同一畫面對照。
- **影像無法互動**：不能縮放、拖曳、點擊查座標，偵測框只能先畫進影像。

另外，產品資料庫的**冷啟動**需要一個上傳工具：組員上傳包裝照片（正面、條碼、營養標示），經前處理後人工確認條碼與營養數值，再寫入產品資料庫。這個工具要**寫資料庫**，依 ADR 0001 只能由 Go 執行；它要**上線給組員使用**（沒有外部人員），需要登入。

限制：

- ADR 0001：Flutter ↔ Go 用 REST（OpenAPI），Go ↔ Python 用 gRPC；Go 是資料庫唯一寫入者。
- 規格（`openapi/`、`proto/`、`db/migrations/`）的變更須由人主導並在 PR 說明。
- 數字由程式或人工確認決定，不採用 LLM 輸出的數字。
- 目前 Go 只有 `/healthz`，Python 的 gRPC 服務尚未實作（規劃書 14.11 的串接驗證還沒做）。

## 決策

1. **前端**：新增頂層資料夾 `workbench/`，以 Vite＋React＋TypeScript 實作；UI 用 Tailwind＋shadcn/ui，資料存取用 TanStack Query，型別由 OpenAPI 產生（`workbench/src/api/gen/`，不手改）。
2. **只經過 Go**：React 只呼叫 Go；Go 再以 gRPC 呼叫 Python。工作台路由與主 API 在**同一個 Go 執行檔**，路徑前綴 `/workbench/v1`，規格另寫在 `openapi/workbench.yaml`，不與 APP 的 `openapi.yaml` 混在一起。
3. **gRPC 分兩個服務**：
   - `PreprocessService`（正式）：品質檢查、條碼逐步升級、發票雙 QR、營養標示、食物照片。欄位全部明確定型；工作台與日後的 APP 流程、冷啟動工具共用。
   - `WorkbenchService`（開發用）：暫存影像、合成影像、模擬退化、診斷影像（邊緣響應、遮罩等）、參數掃描、資料夾批次、E1。Python 只在開發模式註冊這個服務。
4. **設定值以 JSON 傳遞**：設定的結構由 Python 依 `param()` 宣告回傳（`GetConfigSchemas`），React 據此自動產生表單；請求只帶「與預設值不同的欄位」的 JSON，Python 以 dataclass 建構並驗證。這樣新增或修改參數欄位不必改 proto。
5. **影像只上傳一次**：Python 暫存影像並回傳 `image_id`，之後的請求只帶 `image_id` 與參數；幾何結果（框、四角、橢圓）回傳座標，由前端以 SVG 疊圖；影像型結果（遮罩、熱度圖、校正後影像）以 `artifact_id` 透過 Go 取得。
6. **兩種使用範圍**：
   - **開發工具**（模組一各頁、掃描、批次、E1）：只在本機開發模式啟用（`WORKBENCH_DEV_TOOLS=1`），因為會讀取本機檔案與研究資料夾。
   - **冷啟動上傳**：可上線，須以帳號密碼登入；照片存 MinIO，產品資料由 Go 寫入資料庫，並記錄由誰確認。
7. **營養數值第一版由人工輸入**：模組二的欄位解析完成前，冷啟動工具顯示校正後的標示影像，由組員對照輸入；Go 以確定性規則檢查（例如熱量與三大營養素換算差距過大時警告）。模組二完成後改為自動帶入、人工確認。
8. **移除「測試與檢查」頁**：短期用不到，改用終端機與 CI。
9. **漸進遷移**：Streamlit 版保留到 React 版功能齊全（任務書階段 4）後才移除；`ai/workbench/wb/` 的純邏輯搬到 `dietai.devtools`，供 gRPC 服務使用，不重寫。

## 考慮過的其他方案

| 方案 | 優點 | 缺點 | 未採用原因 |
| --- | --- | --- | --- |
| 繼續用 Streamlit | 不用遷移 | 見「情境」 | 整頁重跑與版面限制是框架本身的特性 |
| NiceGUI（純 Python） | 只需 Python、可局部更新、版面元件齊全 | 生態較小；寫資料庫的冷啟動工具仍要另接 Go | 冷啟動工具要接 Go，前端與 Go 之間需要正式 API，React 生態較完整 |
| React 直接呼叫 Python（FastAPI） | 少一層、延遲較低 | 違反 ADR 0001 的通訊分工；Python 不能寫資料庫，冷啟動工具仍要另接 Go，前端得同時對兩個後端 | 分工不一致，日後維護兩套 API |
| 另開 `cmd/workbench` 執行檔 | 與主 API 隔離 | 冷啟動工具要用到 product service，跨執行檔共用較麻煩；部署多一個服務 | 以路由前綴與開關隔離即可 |
| 設定值也做成 proto 欄位 | 型別最嚴謹 | 每改一個參數就要改 proto（需人工審核） | 參數仍在校準、變動頻繁；結構由 `param()` 單一來源提供 |

## 後果

**好處**
- 版面、外觀、影像互動不受框架限制；調參數只更新結果區。
- 順帶完成 Go ↔ Python gRPC 串接（規劃書 14.11），`PreprocessService` 直接供日後 APP 流程使用。
- 冷啟動工具與開發工具共用同一套前端、同一個 Go 服務。

**代價**
- 三種語言都要維護；組員至少一人熟悉 React。
- 每個請求多經過一層（React → Go → Python）；階段 1 須實測延遲（目標：本機調參 < 200 ms）。
- 新增規格檔：`proto/dietai/v1/preprocess.proto`、`workbench.proto`、`openapi/workbench.yaml`，以及冷啟動用的資料表 migration，均須經人工審核。

**後續事項**
- 實作步驟、規格草稿與驗收標準見 `docs/tasks/workbench-react.md`。
- 部署位置（線上版）尚未決定；決定後補寫部署方式（HTTPS、Cookie 設定、備份）。
- 產品資料表須與規劃書 6.1、9.2 對齊後才寫 migration。
- 更新 `.github/CODEOWNERS`（新增 `/workbench/`，並把佔位帳號換成實際帳號）。
