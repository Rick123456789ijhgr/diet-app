# 0001. 採用 Flutter＋Go＋Python 三服務架構，並以單一 monorepo 管理

- 狀態：已採納
- 日期：2026-10-07
- 決策者：全體組員

## 情境

本專題需同時滿足兩種需求：一是可實際使用的行動 APP（拍照、即時掃描、圖表），二是可重現的研究實驗（影像前處理消融、OCR 方案對照、LLM 校正）。研究所需的 OpenCV、PaddleOCR、pandas、PuLP 生態集中在 Python；而 API 路由、資料存取、長時間任務管理與 SSE 推送需要穩定、型別嚴謹且易於部署的後端。

團隊為四人，專題期程約兩年，成員的語言熟悉度不一；並計畫大量使用 AI 程式工具輔助開發，需要明確、可被工具讀取的架構規則。

## 決策

1. **三服務分工**
   - Flutter：使用者介面、即時掃描、簡易品質檢查與影像壓縮。
   - Go 主伺服器：API、身分驗證、資料存取、任務管理與 SSE、營養計算等確定性業務邏輯。
   - Python 外掛服務：影像前處理、OCR、LLM／VLM 呼叫與校正、缺口偵測與建議、研究實驗。
2. **通訊方式**：Flutter ↔ Go 使用 RESTful（OpenAPI）；Go ↔ Python 使用 gRPC（.proto）；Go → Flutter 以 SSE 推送進度。
3. **資料擁有權**：Go 是資料庫唯一寫入者並管理 migration；Python 以唯讀帳號讀取資料庫 view，計算結果經 gRPC 回傳由 Go 寫入。
4. **規格優先**：先寫 OpenAPI 與 .proto，再產生各端程式碼；CI 檢查規格相容性。
5. **單一 monorepo**：三個服務、規格、migration、研究實驗與文件放在同一個儲存庫。

## 考慮過的其他方案

| 方案 | 優點 | 缺點 | 未採用原因 |
| --- | --- | --- | --- |
| 純 Python 後端（FastAPI） | 只需學一種後端語言 | API 與研究程式碼易混雜；長時間任務與即時推送較難做穩 | 希望把確定性業務邏輯與研究實驗明確隔開 |
| 純 Go 後端 | 部署單純 | 影像處理、OCR、統計生態薄弱 | 研究核心依賴 Python 生態 |
| 多儲存庫（每服務一個 repo） | 權限與發佈獨立 | 規格變更須跨 repo 同步；四人團隊管理成本高 | 規格與程式碼需能在同一個 PR 中原子性變更 |
| PWA | 不需處理 APP 發佈 | 相機、即時掃描、背景行為受限 | 需要原生掃描體驗 |

## 後果

**好處**
- 研究程式碼與系統共用同一套 Python 套件，論文數據與實際系統行為一致。
- 規格、migration 與程式碼可在同一個 PR 中變更並審查，CI 可依變更資料夾只跑對應測試。
- Go 唯一寫入者原則讓資料一致性與權限控管單純。

**代價**
- 三種語言的學習成本：至少一位組員深入 Go，且每個服務至少兩人熟悉（見 CODEOWNERS）。
- 本地環境較複雜：以 Docker Compose 一鍵啟動緩解。
- 跨服務除錯較難：每個請求產生 request_id，Go 與 Python 日誌皆記錄。

**後續事項**
- 以 1 至 2 週完成技術驗證原型（規劃書 14.11）。
- Python 讀取的資料庫 view 清單需在 `db/` 中明確定義，作為 Go 與 Python 之間的資料契約。
