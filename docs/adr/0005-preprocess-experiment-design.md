# 0005. 前處理實驗改為「每個方法都執行」的結果表，並以原始樣本為統計單位

- 狀態：提議中
- 日期：2026-11-02
- 決策者：Rick

## 情境

ADR 0004 把模組一的範圍限定為靜態照片，重心放在營養標示，但沒有規定「前處理是否有效」要怎麼證明。
目前的 E1 實驗有幾個問題，使結論站不住：

1. **只做逐步加入**：`a0`～`a6` 一次加一個方法，只能看出「依這個順序加入時」每一步的貢獻，
   看不出單一方法的獨立效果、其他順序，或方法之間是否互相干擾。
2. **讀到就停**：`decode_with_ladder` 第一次有結果即停止，`attempts.csv` 只記到成功那一步，事後無法計算其他組合。
3. **基準組太弱**：合成資料上，zxing-cpp 不做前處理為 46.1%，換成 pyzbar 不做前處理就有 79.7%，
   zxing-cpp 加上前處理為 88.3%。以 zxing-cpp 的 `a0_raw`（37.5%）為基準，會嚴重高估前處理的效果。
4. **把變體當成獨立樣本**：同一個條碼產生的 16 個變體高度相關，以變體為單位計算 Wilson 區間與 McNemar，信賴區間會窄得不真實。
5. **資料是程式畫的條碼**：與真實包裝差距大（例如白紙底在未退化時就被判為過亮）。
6. **營養標示只評到定位**：工作台的退化掃描已能以合成場景的真實四角評估定位（`feat/workbench-label-sweep`），
   但沒有欄位真值、沒有 OCR，無法說明前處理是否讓營養數值讀得更準。
7. **品質門檻沒有依據**：門檻與前處理參數分開調整，沒有對照結果。

研究組另外擬了一份實驗設計初稿，經檢查後與本專案的範圍、規則 5（不訓練）、規則 7（test 鎖定）對齊，
修訂版為 `docs/preprocess-experiment-design.md`。本 ADR 記錄其中會改變程式與實驗流程的決定。

## 決策

以 `docs/preprocess-experiment-design.md` 作為模組一前處理實驗的設計依據，具體為：

1. **資料**：以真實照片為原圖，由程式產生參數已知的劣化變體（半合成）；另收真實拍攝的劣化照片。
   兩者分開報告，正式結論以真實照片為準。規模以「不同產品／發票」計算，不以變體數計算。
2. **切分**：以原始樣本為單位分成 dev／test（不設 train），同一原圖的所有變體跟著原圖走。
   方法選擇、參數、規則與門檻只依 dev 調整；test 在全部定案後只執行一次（規則 7）。
3. **階段零：先選定辨識引擎**。在 dev 上比較候選引擎（皆不做前處理），選定後於所有前處理實驗中固定使用。
   報告時並列其他引擎「不做前處理」的結果。
4. **每個方法都執行**：評測時每個變體執行所有單一方法，不提早停止，輸出「變體 × 方法」結果表
   （正確／誤讀／未讀到，以及耗時）。各方法都從原圖獨立處理，因此任何逐步升級的「方法子集＋順序」
   都能由結果表離線算出；以貪婪法選擇步驟與順序。
5. **疊加流程另行執行**：同一張影像依序做多種處理的固定流程無法由結果表推算，須新增實作；
   只列有影像處理依據的組合，不窮舉。
6. **自適應策略只用規則**：依品質量測值（模糊、亮度、對比、雜訊、傾斜、解析度、反光）選擇處理方式；
   品質檢查的門檻設在最佳策略成功率開始下滑的劣化程度（延續 ADR 0004 第 4 點）。
7. **判定與選擇準則**：結果分為正確、誤讀、未讀到（電子發票 QR 另有部分），另以負樣本量測誤報。
   正式實驗前寫定準則：誤讀率不超過上限的前提下，成功率最高；差距在容許範圍內時選耗時較短者。
   兩個數值寫入實驗 README 後不得修改。
8. **營養標示指標**：主要指標為關鍵欄位（數值＋單位）完全正確率；次要為表格定位誤差與 CER。不使用 WER、TEDS。
9. **統計單位為原始樣本**：信賴區間以 `source_id` 集群 bootstrap 計算，輔以混合效果邏輯迴歸；
   每項任務事先寫定一個主要比較（選定策略 vs Baseline，於真實影像 test），其餘以 Holm 法校正並標示為探索性。
10. **優先順序**：商品條碼（驗證整套流程）→ 營養標示（主要貢獻）→ 電子發票 QR。

現有的 `a0`～`a6`、`m*`、`z*`、`p*` 設定檔與合成資料執行結果保留，作為探索紀錄，不作為正式結論。

## 考慮過的其他方案

| 方案 | 優點 | 缺點 | 未採用原因 |
| --- | --- | --- | --- |
| 維持現狀（逐步加入＋讀到就停） | 不需改程式 | 看不出單一方法效果與交互作用；基準太弱；信賴區間失真 | 結論站不住 |
| 窮舉所有組合，每組實際執行 | 概念直觀 | 7 個方法有 127 種子集，加上順序更多；運算量大，且挑最高分的組會過度擬合 | 結果表可離線算出所有逐步升級組合，運算一次即可；選擇改用貪婪法 |
| 只用合成條碼（現行） | 退化參數精準、不需拍照 | 與真實包裝差距大 | 改為真實照片當原圖，保留可控性 |
| 以變體為單位做 McNemar | 實作簡單（已有） | 變體不獨立，p 值偏小 | 改以原始樣本為單位；McNemar 只用在每個原圖只有一個變體的情況 |
| 自適應策略用機器學習分類器 | 可能較準 | 規則 5 禁止訓練神經網路；需要另外的訓練集 | 規則與統計方法已能檢驗假設 |
| 營養標示以 CER、TEDS 為主要指標 | 一般文件 OCR 常用 | 不直接反映營養數值是否正確；TEDS 標註成本高 | 本專案要的是欄位數值 |

## 後果

- 好處：每個方法的獨立效果、所有逐步升級組合、方法間的干擾都能從同一份資料回答；
  基準與統計單位正確，結論可以寫進論文；品質門檻有了依據。
- 代價：
  - 「每個方法都執行」的評測比讀到就停慢，約為方法數倍；離線評測可以接受，上線流程不受影響。
  - 需要拍攝與標記真實照片（每項任務 100～200 個不同樣本），營養標示須兩人獨立標記。
  - 正式實驗前要先完成階段零，條碼的正式結論會比原計畫晚。
- 後續工作（各自一個 PR，皆須附測試）：
  1. `dietai.evaluation`：新增「每個方法都執行」模式與結果表；離線計算逐步升級與貪婪選擇。
  2. `dietai.evaluation.stats`：以原始樣本為單位的 bootstrap、Holm 校正。
  3. `dietai.devtools.degradations`：補上手震模糊、椒鹽雜訊、對比降低、JPEG、曲面；
     新增由真實照片產生變體與 manifest 的腳本（manifest 加 `source_id`）。
  4. `dietai.preprocess`：疊加型固定流程（設定格式要先定，可能牽動 `LadderConfig`）。
  5. 營養標示：選定 OCR 引擎、欄位真值格式、欄位正確率與定位誤差評估；實驗資料夾與編號待規劃書確認。
  6. 規則式自適應策略。
- 若工作台要顯示結果表或新增營養標示的掃描頁，涉及 `openapi/`／`proto/` 變更，須由 Rick 另行同意（規則 3）。
- E1 README 的「結論」一節改依本設計填寫；原有合成資料的結果移到「探索紀錄」。
