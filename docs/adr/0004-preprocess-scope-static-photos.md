# 0004. 伺服器端影像前處理只服務無法重拍的靜態照片

- 狀態：已採納
- 日期：2026-11-02
- 決策者：Rick

## 情境

模組一的條碼逐步升級（`preprocess.barcode`）與 E1 消融，研究的都是「一張靜態照片經過前處理後能否解出條碼」。
但一般 APP 掃條碼時是相機預覽**連續解碼**：每秒試數十張畫面，解不出來時使用者自己調整角度與距離，
直到解出為止。使用者的手就是最有效的「前處理」，伺服器端修補對即時掃描的意義不大。

同時，工作台原本可以分別調整前處理參數與品質門檻，兩者都沒有對照標準答案，調整結果只能憑肉眼判斷；
參數掃描頁的條碼成功率也只看「有沒有解出」，讀成另一個檢查碼正確的號碼（誤讀）也算成功。

## 決策

1. **APP 的條碼與電子發票 QR 走即時掃描**，使用現成的手機端掃描套件，不經伺服器的逐步升級。
2. **伺服器端前處理只服務無法重拍的靜態照片**：相簿匯入、截圖、冷啟動上傳。前處理的心力集中在
   營養標示（一定是靜態照片，且 OCR 需要校正後的影像）；食物照片以切出各道菜與壓縮為主。
3. **E1 的結論範圍限定為靜態照片**，不外推到即時掃描。
4. **工作台調參改以「已知程度的退化 → 前處理參數 → 對真值的結果」為主**：
   - 成功率只計讀對的樣本，誤讀另列（判定沿用 E1 的 `dietai.evaluation.barcode.judge`）。
   - 品質門檻不獨立調整：先把前處理調好，再看逐步升級成功率從哪個退化等級開始下滑，門檻設在那裡。
     工作台以「誤報」（品質不通過但其實讀得對）與「漏報」（品質通過但讀不對）呈現兩者的落差。
   - 營養標示比照辦理，以合成場景的真實四角評估定位（後續 PR）。
   - 合成退化只用來找方向與範圍；最後數值以真實照片的 dev split 確認，不得使用 test split（規則 7）。

## 考慮過的其他方案

| 方案 | 優點 | 缺點 | 未採用原因 |
| --- | --- | --- | --- |
| 研究改為即時掃描實測（比較手機套件直接掃描與加上即時提示，量測掃到所需時間與誤讀率） | 貼近使用者實際體驗 | 需錄影或真人實測，資料收集成本高；E1 現有結果用不上 | 人力與時程不足；靜態照片仍是冷啟動上傳與相簿匯入的真實情境 |
| 維持現狀，前處理參數與品質門檻分開調 | 不需改動 | 沒有標準答案，調整無法驗證；誤讀被算成成功 | 調參結果沒有意義 |

## 後果

- 條碼逐步升級保留，但只用於冷啟動上傳與相簿匯入；APP 端 `scan` 實作時直接採用手機端掃描套件。
- 工作台參數掃描頁的條碼結果改為對真值判定，新增誤讀率與「品質門檻對照」（PR：feat/workbench-sweep-truth）。
  合成條碼的白紙底在未退化時就觸發「過亮」，顯示 `bright_ratio_max` 對白色包裝過嚴，須以真實照片校準。
- 營養標示的退化掃描（`SweepRequest.target` 加上 `label`，規格變更經 Rick 同意；PR：feat/workbench-label-sweep）：
  合成標示的真實四角隨幾何退化一起換算，判定正確／偏移／找不到。新增「透視強度」退化。
  掃描用的旋轉與透視改以延伸邊緣像素補空白：白色填邊會形成人工外框，定位會把它誤認成表格框
  （合成資料的假失敗，真實照片沒有這種外框）。
- 後續：真實照片（dev split）的營養標示定位驗證。
- 即時掃描若之後要研究（例如加入即時品質提示），須另立 ADR 取代本決策的第 3 點。
