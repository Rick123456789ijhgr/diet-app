# M2 全專案 code review 規劃書

> 狀態：規劃中（尚未開始逐檔審查）  
> 日期：2026-10-24  
> 基準：`main` 的 `c4c18de`（M1 審查修正合併後）  
> 本文件只定義審查方法與產出；除本規劃書外，本階段不修改任何檔案。

## 目標

在不變更產品規格與程式碼的前提下，找出會影響資料真實性、營養數字正確性、安全邊界、服務契約及使用者流程的問題，形成可獨立處理的審查清單。

本輪特別驗證 M1 修正是否造成回歸，並將範圍由影像前處理與工作台擴至 Flutter APP、Go API、Python AI、資料庫契約及跨服務流程。

## 審查範圍與優先順序

| 順序 | 範圍 | 重點 |
| --- | --- | --- |
| 0 | 專案規範與變更基準 | 讀取根目錄及各目標資料夾的 `CLAUDE.md`；確認目前分支、未提交變更、M1 修正提交與測試狀態。 |
| 1 | 跨服務契約 | 比對 `openapi/`、`proto/`、`db/migrations/` 與呼叫端；確認欄位、錯誤碼、單位、nullable、版本相容性與產生碼邊界。只讀取，不建議或進行規格檔修改。 |
| 2 | 資料真實性與寫入路徑 | 追蹤 APP → Go → DB、Python → 唯讀 view 的資料流；檢查營養數字是否完全由 DB 或確定性程式得出、Go 是否為唯一 DB 寫入者、金鑰是否只留在 Python。 |
| 3 | Go API（`api/`） | 身分與授權、輸入大小與格式、交易與併發、錯誤轉譯、context 取消、資料庫查詢、HTTP/gRPC 邊界、測試涵蓋。 |
| 4 | Python AI（`ai/`） | 核心與介面依賴方向、設定與門檻來源、影像與檔案限制、RPC 錯誤、型別與例外、決定性與研究程式共用邊界。 |
| 5 | Flutter APP（`app/`） | API token 與敏感資訊、狀態生命週期、離線/重送、輸入與顯示單位、錯誤與載入狀態、中文·English 介面標籤規則、無障礙。 |
| 6 | 工作台與研究（`workbench/`、`research/`） | 僅開發用途是否被隔離、前後端結果是否同一影像/請求配對、前端不得自行決定營養數字、test split 鎖定、研究程式是否只 import `ai/`。 |
| 7 | M1 回歸驗證 | 對照 `docs/reviews/m1-code-review.md` 與其後修正提交，檢查每一項已修正問題的測試、錯誤處理與相鄰邊界，避免只修表面行為。 |

## 風險導向檢查表

### P0：必須優先確認

- 營養素、克數、熱量是否採用 LLM 輸出或未經確定性驗證的數字。
- 是否存在 Python 寫入 DB、APP/Go 持有 LLM 金鑰、或未授權資料寫入路徑。
- 認證、授權、帳戶/食物紀錄隔離與敏感資料外洩。
- migration、OpenAPI、proto 與已產生程式碼間的破壞性不一致。
- 會造成資料遺失、重複寫入、錯誤關聯使用者或錯誤營養計算的流程。

### P1：應在本輪確認

- 輸入驗證、檔案/影像大小、解壓縮炸彈、逾時、取消與重試的資源控制。
- 浮點、單位換算、時區、分頁、排序、空值與極端輸入。
- DB transaction 邊界、idempotency、並行更新與錯誤碼一致性。
- 前後端 API 模型、錯誤顯示與 loading/error/empty 狀態是否一致。
- 設定、門檻和可校準參數是否位於正確 config，且未使用 test split 調整。

### P2：記錄並視影響排序

- 可讀性、死碼、過時註解、型別精確度、測試可維護性與開發體驗。
- 視覺一致性、鍵盤操作、螢幕閱讀器語意及工作台介面中文規則。

## 執行方式

1. 建立審查快照：記錄 commit、工作區狀態、可用的服務/測試指令，以及各服務的在地規範。
2. 先畫出資料流與信任邊界，再逐一從 API handler/RPC 追到 domain 邏輯、資料存取、呼叫端與測試；不只依檔案目錄瀏覽。
3. 每一項疑點以程式閱讀、契約對照及最小化的唯讀/測試驗證交叉確認。測試僅在不修改原始碼、不寫入正式資料且符合各服務規範時執行。
4. 對高風險問題優先找反例與現有測試；證據不足時標示「需確認設計意圖」，不將推測寫成確定缺陷。
5. 審查中不修改程式、規格、migration、產生碼、設定或測試；也不使用 test split 校準任何規則或門檻。
6. 最後交叉檢查同一議題是否已在 M1、既有 issue、測試或文件中被處理，避免重複列案。

## 預定交付格式

完成後在 `docs/reviews/` 新增一份「問題清單」文件（不直接修程式），每個項目都包含：

| 欄位 | 內容 |
| --- | --- |
| ID / 嚴重度 | `P0`、`P1`、`P2` 或「需確認」；以資料正確性與使用者影響排序。 |
| 位置 | 可點擊的檔案與精確行號。 |
| 證據 | 可重現情境、契約/規範依據、閱讀結論及是否已驗證。 |
| 影響 | 錯誤資料、安全、穩定性、相容性或使用體驗的具體後果。 |
| 建議 | 最小修正方向與應補的測試；不直接套用修改。 |
| 處理欄 | 供人工標記「修正／維持／待討論」。 |

「確定錯誤」與「需確認設計意圖」會分區呈現。涉及規格、migration 或門檻校準者會明確標註為需要人類決策，不把它們列為可由 AI 直接修正的項目。
